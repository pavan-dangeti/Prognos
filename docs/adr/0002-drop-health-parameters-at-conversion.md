# ADR-0002: Drop the health parameters and virtual sensors at the conversion boundary

Date: 2026-10-09
Status: Accepted (revised 2026-10-09 after reading the actual files)

## Context

Each N-CMAPSS sub-dataset HDF5 file stores flat matrices, one row per sensor
reading, with a parallel array of variable names:

- `A` — `unit`, `cycle`, flight class, health state
- `W` — scenario descriptors (`alt`, `Mach`, `TRA`, `T2`). Known on a real aircraft
  before the engine starts.
- `X_s` — 14 measured condition-monitoring signals. This is what sensors produce.
- `X_v` — 14 virtual sensor estimates, inferred from the health parameters.
- `T` — 10 true health parameters, the per-module `*_eff_mod` and `*_flow_mod`
  degradation values.
- `Y` — the RUL label.

`T` is generated by the same simulator process that generates `X_s`. It is not
merely correlated with RUL; it is close to a linear encoding of it. A model given `T`
will score well and predict nothing useful, because no equivalent signal exists on a
real engine.

An earlier version of this record described per-unit HDF5 groups and called the
health parameters `theta`. That was wrong on both counts. The hazard is the same; the
names were not.

## Decision

The HDF5 to Parquet converter reads only `A`, `W`, `X_s` and `Y`. `T` and `X_v` are
never loaded, so they cannot reach Parquet, and downstream code cannot reach them.
Model input matrices are built from an explicit column allowlist, and a test asserts
that no leaking column survives into any model input.

## Rationale

Dropping at the conversion boundary makes the guarantee structural rather than
conventional. The dangerous path is a filter applied at training time and forgotten
at inference time, or a feature builder that reaches for whatever is in the frame. If
the columns do not exist downstream of conversion, neither mistake can happen.

Not reading them at all is stronger than reading and dropping them. A filter that
runs after `load()` is one refactor away from being applied in the wrong place, and
the health parameters are tempting enough that someone will want them.

The allowlist plus test is the second line of defence: it catches a future
contributor who adds a column directly from HDF5, bypassing the converter.

## Consequences

- Direct comparison against published hybrid results that use calibrated sensor
  estimates or health parameters is not possible on equal footing. We compare against
  the data-driven setting (`W` + `X_s`) instead, and say so where the setups differ.
- The conversion is not reusable for health-indicator work that legitimately needs
  `T`. If that is ever wanted, it needs a separate, clearly labelled conversion path
  and its own leakage discussion.

## Alternatives

- Carry all groups and filter at training time: rejected, the filter becomes
  load-bearing and silently omittable.
- Carry all groups and filter in the model wrapper: rejected, same problem one layer
  up.
- Carry `X_v` as an extra input channel: rejected. It is computed from `T`, so it
  carries the same information through a different door.
